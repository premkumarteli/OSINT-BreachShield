P65: ABSTRACT

P66: BreachShield is a breach-intelligence platform that lets a user find out whether an email address or phone number appears in known breach data without handing that identifier to the server. The browser hashes the identifier with SHA-256 and sends only the first five hexadecimal characters; the server returns the matching bucket and the browser completes the comparison locally. Access is gated by a one-time password delivered by email, or by SMS through a companion Android gateway, and a signed JWT carries the verified session.

P67: A search is dispatched to a pluggable set of source adapters. A local breach catalog and a Telegram channel scraper are live; two further adapters are registered but are placeholders. The combined result text is scored by a regex-based exposure risk engine, and a pretrained URL-transformer classifier contributes to the score when URLs are present. A separate XGBoost severity classifier, trained on 1,034 breach records, reaches 89.2% test accuracy against 66.2% for a 1D-CNN, 48.4% for a Transformer and 44.6% for an RNN; it is kept as a research artefact and is not part of the production risk score.

P68: Every search is recorded in an audit log whose entries are hashed into Merkle batches of up to 100 entries or 60 seconds and anchored by a smart contract on a local Ethereum-compatible chain. The backend and frontend test suites pass (101/101 and 50/50). The report also states what does not work yet: automatic contract deployment needs a deployer key, two of the four source adapters make no network calls, and the CRITICAL severity class has only nine test records.

P158: CHAPTER 1

P159: INTRODUCTION

P160: 1.1  Overview

P161: BreachShield is a web platform that tells a user whether an email address or phone number appears in known data-breach records. Its main design rule is that the identifier itself should not be sent to the server. The browser computes a SHA-256 hash of the identifier, sends only the first five hexadecimal characters of that hash, receives the stored records whose hashes start with those five characters, and checks for an exact match on its own side. This is the range-query idea used by public password-checking services, which rests on the k-anonymity model [2], [3].

P162: Around this search the system provides one-time-password (OTP) login by email or SMS, a registry of breach-source adapters (a local breach catalog and a Telegram channel scraper are live), an exposure risk score, a pretrained URL-transformer classifier for phishing links found in results, and an audit log. The audit log is hashed into Merkle trees in batches and the tree roots are anchored by a smart contract on a local Ethereum-compatible chain, so that later changes to logged events can be detected.

P163: The project is built as four tiers: a React 19 frontend, an Express 5 API gateway in Node.js, a Python FastAPI microservice for Telegram collection and machine-learning inference, and an Android (Kotlin) application that relays OTP messages as SMS. A separate XGBoost model classifies breach severity. It was trained and benchmarked against three neural models, but it is not used in the production risk score (Section 7.8).

P164: Project Phase 1 proposed a wider suite: a browser extension, a vulnerability scanner, continuous dark-web crawling and cloud deployment. During Phase 2 we narrowed the work to the parts we could build and verify. Section 1.4 lists exactly what is and is not included.

P165: 1.2  Motivation

P166: Credential leaks are common and expensive. IBM’s 2024 Cost of a Data Breach report puts the global average cost of a breach at USD 4.88 million and names stolen or compromised credentials as the most frequent initial attack vector, at 16% of the breaches studied [1]. Most people find out that their data was exposed only after something goes wrong.

P167: Checking whether an account has been exposed creates its own privacy problem. A typical breach-lookup service asks the user to type the full email address or phone number into a third-party server. That server then holds a list of identifiers that someone was worried about, which is itself sensitive. We wanted to see how far a breach-checking service could go in avoiding this, while still giving the user a useful answer.

P168: Breach information is also scattered. Some of it sits in public breach catalogs; some appears first in Telegram channels. A single tool that queries several sources and gives one consolidated, explainable answer is more useful than separate manual checks. Finally, a service that records who searched for what should itself be accountable. A tamper-evident audit trail was therefore part of the design from the start.

P169: 1.3  Objectives

P170: 1.	To design a breach-search protocol in which the raw identifier never leaves the browser and the server sees only a 20-bit hash prefix.

P171: 2.	To authenticate users with an OTP sent by email or SMS and to bind the search session to the verified identity.

P172: 3.	To query more than one breach source through a common adapter interface and to keep the search working when one source fails.

P173: 4.	To compute an explainable exposure risk score from the aggregated results, and to flag phishing URLs with a pretrained classifier.

P174: 5.	To train and honestly benchmark a breach-severity classifier, comparing a tree-based model with neural models on the same data.

P175: 6.	To record every search in a tamper-evident audit log anchored on a blockchain.

P176: 7.	To test the system and to report verified results and known limitations separately from planned work.

P177: 1.4  Scope

P178: Included in this report. Client-side SHA-256 hashing and range-query search; OTP login with email and SMS delivery; JWT sessions; a local breach store; a Telegram scraper source; regex-based exposure risk scoring; UrlBERT phishing-URL classification; an XGBoost severity classifier and its benchmark; Merkle-batched audit logging with a Solidity anchor contract on a local Hardhat chain; an Android SMS gateway; and the web dashboard.

P179: Not included. The browser extension, the website vulnerability scanner, continuous crawling of dark-web forums beyond one Telegram channel, and cloud deployment, all of which were proposed in Phase 1. The two source adapters for phishing feeds and threat intelligence are registered in the code but do not yet make network calls. The system is a prototype and has not been load-tested or deployed publicly.

P180: 1.5  Existing System

P181: Public breach-notification services let users search by email address, and the search request carries the full address to the service. Services for checking passwords improved on this by using a prefix range query, in which only part of a password hash is sent [3]. The same idea is not generally offered for email and phone lookups, and prefix-based checking has known limits that have been analysed in the literature [3].

P182: Threat-intelligence tools, on the other hand, are written for security analysts. They collect feeds, dark-web posts and indicators of compromise, but they do not give an ordinary user a private way to ask a simple question. Neither category usually provides an audit trail that the operator cannot quietly edit. Most logs are ordinary database rows or text files that anyone with write access can change.

P183: 1.6  Proposed System

P184: BreachShield combines the missing pieces into one prototype. The browser hashes the identifier and sends a five-character prefix. The gateway authenticates the user, queries the registered sources in parallel, and tolerates failure of any one of them. A risk engine converts the aggregated text into a score between 20 and 100 and a four-level label (LOW, MEDIUM, HIGH, CRITICAL). A pretrained transformer checks any URLs found in the results for phishing.

P185: Each search is written to an audit log. Log entries are canonicalised and hashed, grouped into Merkle trees of up to 100 entries or 60 seconds, and the root of each tree is stored by a smart contract. Changing an anchored entry later would change its tree root and would no longer match the stored value. Chapter 6 describes the design in detail and the Conclusion lists the open limitations. In particular, the anchoring runs on a local development chain, so the roots are not publicly verifiable.

P186: CHAPTER 2

P187: PROBLEM STATEMENT

P188: 2.1  Problem Statement

P189: Checking whether a personal identifier has been exposed in a data breach normally requires the user to submit that identifier to a third-party server. This turns a protective action into a privacy risk, and it discourages people from checking at all. At the same time, breach information is spread across catalogs and Telegram channels, results are reported without any explanation of how serious they are, and the services that operate these lookups usually keep logs that the operator could alter without detection.

P190: The problem addressed by this project is therefore to build a breach-lookup service in which (a) the raw identifier is never sent to the server, (b) access is limited to verified users, (c) results from several sources are combined into one explainable risk assessment, and (d) every search is recorded in a log whose later modification can be detected.

P191: 2.2  Motivation

P192: Two things motivated the narrower Phase 2 problem. First, the privacy argument above: a lookup service should not learn what the user is looking for. Second, our own audits showed how easy it is for a security project to claim more than it does. Parts of the first prototype presented placeholder code as working features. We decided that the Phase 2 system, and this report, should state plainly which parts are verified and which are not, and that the evaluation should be reproducible from the repository.

P193: 2.3  Objectives

P194: Hide the identifier from the server during search, leaking at most a 20-bit hash prefix.

P195: Gate search by OTP-verified identity, with rate limits and hashed OTP storage.

P196: Query multiple sources through one adapter interface and keep working when a source or the AI service is unavailable.

P197: Produce an explainable score from the combined results, with each contributing factor visible.

P198: Compare tree-based and neural classifiers for breach severity on one dataset, and report the result whether or not the model is deployed.

P199: Make the audit log tamper-evident using Merkle batching and an on-chain anchor.

P200: Verify each claim by running the code, and report open problems as findings.

P202: DETAILED SURVEY

P203: The Phase 1 survey listed ten references, several with incomplete or unverifiable publication details, so we replaced it for this report. Every paper below was looked up, and each summary says what we took from it. Reference numbering follows the order of first citation in the report, so the numbering starts at [2] here; reference [1], the IBM report, is cited in Chapter 1.

P204: [2]  L. Sweeney, "k-Anonymity: A Model for Protecting Privacy," Int. J. Uncertainty, Fuzziness and Knowledge-Based Systems, 2002.

P205: Problem: Releasing records without identifying individuals. Approach: Defines k-anonymity: each released record must be indistinguishable from at least k−1 others with respect to identifying attributes. What we took from it: The hash-prefix bucket plays the role of the anonymity set in our search protocol. We use the idea, not the full formal model.

P206: [3]  L. Li, B. Pal, J. Ali, N. Sullivan, R. Chatterjee and T. Ristenpart, "Protocols for Checking Compromised Credentials," ACM CCS, 2019.

P207: Problem: Privacy of services that check whether credentials appear in breaches. Approach: Analyses hash-prefix checking protocols as deployed and proposes stronger alternatives with higher cost. What we took from it: Our protocol follows the simpler prefix design. The paper tells us what that design does not protect, which we list as a limitation.

P208: [4]  K. El Emam and F. K. Dankar, "Protecting Privacy Using k-Anonymity," J. Am. Med. Inform. Assoc., 2008.

P209: Problem: Choosing k and measuring re-identification risk for health data. Approach: Discusses how the strength of k-anonymity depends on the data and on the chosen k. What we took from it: Reminds us that the privacy of a bucket depends on how many identifiers can share a prefix, not only on the prefix length.

P210: [5]  R. C. Merkle, "A Digital Signature Based on a Conventional Encryption Function," CRYPTO ’87, 1988.

P211: Problem: Authenticating many values with one short value. Approach: Introduces the hash tree: leaves are hashed and combined pairwise up to a single root. What we took from it: Basis of our audit batching. One anchored root commits to up to 100 log entries.

P212: [6]  S. A. Crosby and D. S. Wallach, "Efficient Data Structures for Tamper-Evident Logging," USENIX Security, 2009.

P213: Problem: Detecting tampering in append-only logs. Approach: Proposes a history tree that supports efficient membership and consistency proofs. What we took from it: Shows what a stronger audit log offers. Ours does not yet provide consistency proofs between batches.

P214: [7]  A. Arabnouri, S. Eissazadeh and A. Shafieinejad, "A Secure Auditable Log Based on Blockchain," Monadi, vol. 13, no. 2, 2024.

P215: Problem: Storing audit logs on a blockchain without the scalability cost of writing every entry. Approach: Groups logs into time intervals, chains entries with message authentication codes, and writes each interval as a batch at a checkpoint. What we took from it: Supports our decision to batch entries instead of writing each to the chain.

P216: [8]  T. Chen and C. Guestrin, "XGBoost: A Scalable Tree Boosting System," ACM SIGKDD, 2016.

P217: Problem: Scalable gradient-boosted decision trees. Approach: Regularised tree boosting with efficient handling of sparse data. What we took from it: The model we use for breach-severity classification.

P218: [9]  L. Grinsztajn, E. Oyallon and G. Varoquaux, "Why Do Tree-Based Models Still Outperform Deep Learning on Typical Tabular Data?," NeurIPS, 2022.

P219: Problem: Which model family works best on tabular data. Approach: Benchmarks tree-based and neural models on many tabular datasets and finds trees ahead on medium-sized data. What we took from it: Matches what we saw: XGBoost beat the CNN, Transformer and RNN on our 1,034 records.

P220: [10]  A. Aljofey, Q. Jiang, Q. Qu, M. Huang and J.-P. Niyigena, "An Effective Phishing Detection Model Based on Character Level Convolutional Neural Network from URL," Electronics, 2020.

P221: Problem: Detecting phishing from the URL alone. Approach: A character-level CNN reads the raw URL string, avoiding hand-built features. What we took from it: Background for using a learned URL classifier on links found in breach results.

P222: [11]  O. K. Sahingoz, E. Buber and E. Kugu, "DEPHIDES: Deep Learning Based Phishing Detection System," IEEE Access, 2024.

P223: Problem: Phishing detection with deep learning on large URL datasets. Approach: Compares several deep architectures on a large URL dataset. What we took from it: Further support for deep models on URL text. Our deployed classifier is a pretrained transformer for the same task.

P224: [12]  B. V. Pavani, D. Mahitha and B. Uma Maheswari, "Enhancing Online Safety: Phishing URL Detection Using Machine Learning and Explainable AI," ICCCNT, 2024.

P225: Problem: Explaining why a URL was flagged. Approach: Combines machine-learning classifiers with explainability methods. What we took from it: Motivates showing the factors behind a score rather than a single number.

P226: [13]  P. Kühn, K. Wittorf and C. Reuter, "Navigating the Shadows: Manual and Semi-Automated Evaluation of the Dark Web for Cyber Threat Intelligence," IEEE Access, 2024.

P227: Problem: Practical value and difficulty of collecting threat intelligence from the dark web. Approach: Evaluates manual and semi-automated collection methods. What we took from it: Explains why we limited dark-web collection to one Telegram source instead of broad crawling.

P228: [14]  M. Saleem, R. Islam and M. A. Kabir, "The Anonymity of the Dark Web: A Survey," IEEE Access, 2022.

P229: Problem: How anonymity works on the dark web. Approach: Surveys anonymity networks and the techniques used to study them. What we took from it: Background for the OSINT problem area.

P230: [15]  J. Pastor-Galindo, P. Nespoli, F. Gómez Mármol and G. Martínez Pérez, "The Not Yet Exploited Goldmine of OSINT," IEEE Access, 2020.

P231: Problem: Open-source intelligence tools, uses and open problems. Approach: Surveys OSINT sources, techniques and challenges. What we took from it: Places our pluggable source-registry design in the wider OSINT landscape.

P255: 6.1  System Design

P256: 6.1.1  System Architecture

P257: BreachShield is organised as a monorepo with four tiers (Fig. 6.1). The React frontend does all hashing and prefix handling. The Express gateway owns authentication, the source registry, the risk engine and audit logging. The FastAPI service hosts the Telegram scraper and the machine-learning models. The Android application only relays OTP messages. MySQL (with a JSON-file fallback) stores OTP and session data, the k-anonymity store holds the breach records, and the AnchorRegistry contract on a local Hardhat chain stores Merkle roots.

P259: Fig. 6.1  System architecture of BreachShield

P260: Two design decisions shape the rest of the system. First, hashing happens in the browser, so no later component ever sees the raw identifier for search purposes. Second, the gateway treats every external dependency (a source adapter, the AI service, the database, the chain) as something that can fail, and degrades instead of stopping.

P287: 6.2.5  Scenarios

P288: Scenario 1: normal search. The user verifies an OTP, enters an email address, and the browser sends a 5-character prefix. The gateway returns the bucket, the browser finds a matching suffix, the sources are queried in parallel, the risk engine scores the combined text, and the event is queued for the audit log. The user sees the matched breaches, the score and the contributing factors.

P289: Scenario 2: no match. The bucket contains no entry whose suffix matches. The browser reports no known exposure in the local store, while the live Telegram source may still return text that is scored. The event is still logged.

P290: Scenario 3: a dependency fails. The AI service is unreachable or the Telegram source times out. Promise.allSettled lets the other sources finish. The gateway logs a warning, sets the AI result to null, and returns the remaining results. We tested the AI-service case directly (Chapter 9).

P291: Scenario 4: anchoring fails. The chain call for a batch fails. The batch is moved to a dead-letter queue and recovered on the next start; the user-facing search is unaffected. Automatic deployment of the contract on restart currently fails when the deployer key is not set (Section 7.9).

P292: CHAPTER 7

P293: IMPLEMENTATION

P294: 7.1  Repository Layout

P295: The code is a four-part monorepo: the React frontend, the Express gateway with its tests and blockchain modules, the Python scraper and AI service, and the Android gateway. The Solidity contract and its Hardhat configuration live in a separate contracts directory. This chapter describes each module and states how it was verified.

P296: 7.2  Client-Side k-Anonymity Search

P297: The frontend trims and lowercases the identifier, computes SHA-256 with the Web Crypto API, and splits the 64-character hexadecimal digest into a 5-character prefix P and a 59-character suffix S. Only P is sent, in a request to /api/v1/range/P with the session token. The server returns the stored suffixes in that bucket along with their breach metadata, and the browser keeps the records whose suffix equals S. Algorithm 7.1 gives the procedure.

P298: Algorithm 7.1  Client-side range query

P299: Input : identifier T, session token tau

P300: Output: matched breach metadata R

P301: 1  T' <- toLowerCase(trim(T))

P302: 2  H  <- SHA-256(T')             # computed in the browser

P303: 3  P  <- H[0:5];  S <- H[5:64]

P304: 4  B  <- GET /api/v1/range/P  (Bearer tau)

P305: 5  R  <- empty set

P306: 6  for each (S_i, M_i) in B:

P307: 7      if S_i == S: add M_i to R

P308: 8  return R

P309: There are 16^5 = 1,048,576 possible prefixes, so the prefix discloses at most 20 bits about the identifier. The anonymity of a particular lookup comes from how many possible identifiers share the same prefix, which grows with the population of identifiers and not with the number of records we store. Two limits apply and are stated in the Conclusion: because search is login-gated, the server knows who is searching even though it does not know which identifier in the bucket is being checked [3]; and the quality of the match depends on the browser normalising the identifier exactly as the server did when the record was stored.

P310: Verification: a live round trip (hash, prefix query, suffix match, ingest and lookup) works for email identifiers, where client and server normalisation agree. CONFIRM before submission: in the September 2026 audit, phone-number identifiers typed with spaces, dashes or without the +91 prefix were normalised differently in the browser and on the server and so did not match. State here whether this has been fixed and re-tested.

P311: 7.3  Authentication and OTP

P312: On send-otp the gateway checks a 30-second resend cooldown, generates a six-digit code from a cryptographically secure random integer, hashes it with bcrypt (cost factor 10) and stores the hash with a five-minute expiry. Storage is in MySQL with an automatic fall-back to a JSON file if the database is unavailable. The code is sent by email or, for a phone target, as a DLT-templated SMS relayed through the Android gateway. On verify-otp the stored hash is compared, with at most five attempts in the validity window. Success issues a JWT [16] valid for one hour, carrying the target and a verified flag, returned in the response and set as an HTTP-only cookie. A development flag that skips OTP checks exists in the code and must be off in any real deployment; the backend tests were run with it both on and off.

P313: 7.4  Breach-Source Registry

P314: BreachSource is an abstract class with one method, search(normalizedTarget, targetHash). SearchService holds the list of registered sources and calls all of them with Promise.allSettled, so one failure does not cancel the others. Four adapters are registered. PublicBreachSource reads the local catalog through the k-anonymity store. TelegramScraperSource calls the Python service. PhishingFeedSource and ThreatIntelSource are placeholders that do not call any external feed; they are listed as planned work and not counted as working sources.

P315: 7.5  Telegram OSINT Service

P316: The Python FastAPI service uses Telethon to read configured Telegram channels and return matching text to the gateway. Under simultaneous requests the Telethon session file raised a database-locked error; this was fixed by serialising access to the client with an asyncio lock. Telegram credentials are read from environment variables.

P317: 7.6  Risk-Scoring Engine

P318: The risk engine works on the combined text from all sources. It applies regular expressions for passwords or hashes, phone numbers, email addresses, document numbers, physical addresses and named relations, and adds capped points per category: documents up to 35, password or hash material up to 30, address up to 20, phone up to 15, and multiple independent sources up to 15. A correlation score across records and, when the AI service returns a result, a phishing contribution of up to 30 points (probability times 30) are added. The total is limited to the range 20–100 and mapped to LOW, MEDIUM, HIGH or CRITICAL. Source reliability and recency are computed from the text and not fixed. The factors are returned to the user with the score.

P319: Algorithm 7.2  Exposure risk scoring

P320: Input : aggregated result text X, AI result A

P321: Output: score in [20,100], tier

P322: 1  score <- 0

P323: 2  for c in {doc, password, address, phone, multi-source}:

P324: 3      score <- score + min(match(X, c), cap[c])

P325: 4  score <- score + correlate(X)            # up to 15

P326: 5  if A is present: score <- score + A.phishProb * 30

P327: 6  score <- clamp(score, 20, 100)

P328: 7  return score, threshold(score)

P329: This engine is a transparent rule set, not a trained model. Earlier in the project, three fields in its output were fixed constants presented as computed values. They are now computed from the data, and the source was checked.

P330: 7.7  URL Phishing Classifier (UrlBERT)

P331: When results contain URLs, the gateway calls the FastAPI endpoint /api/ai/analyze-threat, which runs a pretrained Hugging Face URL-transformer classifier. On a known phishing test URL it returned the PHISHING class with probability 0.9999 in about 31 ms. When the text contains no URL the phishing probability is 0 by construction, because the model only scores URLs. A scoping bug in the first version (torch was imported inside a function) made every call fail; it was fixed by moving the import to module level and re-tested against the running service.

P332: 7.8  Breach-Severity Classifier

P333: We trained classifiers to predict the severity tier of a breach from its metadata. The dataset has 1,034 breach records collected from a public breach catalog, split 70/15/15 with a fixed seed into 723 training, 154 validation and 157 test records. Each record is a 165-dimensional feature vector. XGBoost (maximum depth 6, learning rate 0.1) was compared with a 1D-CNN, a Transformer encoder (2 layers, 4 heads) and an RNN, which was retrained with packed sequences and gradient clipping after the first run performed below the naive baseline. Results are in Chapter 9.

P334: The code has two groups of neural models and they must not be confused. The severity models load trained checkpoints from disk and give identical output on repeated calls; they feed the severity block of the analyze-threat endpoint. A separate group of URL-comparison models behind a demonstration endpoint does not load any checkpoint and gives different output on every instantiation. Only the first group is reported here. The XGBoost model is not used in the production risk score, because live sources do not reliably provide the features it was trained on.

P335: 7.9  Merkle Audit Log and Blockchain Anchoring

P336: Each search produces an audit event. The event is canonicalised as sorted-key JSON, hashed with SHA-256 into a leaf, and queued. When the queue reaches 100 leaves or 60 seconds pass, whichever is first, the batch is built into a Merkle tree and the root is sent to the AnchorRegistry smart contract (Solidity 0.8.20) on a local Hardhat chain through ethers.js. Failed batches are moved to a dead-letter queue and recovered on restart. Batching limits the number of chain transactions; in the interval before a batch is anchored, tampering would not yet be caught by the on-chain root.

P337: Current status. The contract compiles. Automatic deployment on restart fails when the deployer private-key environment variable is not set, because the account list is then empty and the deploy script cannot find a deployer address. This is a configuration fault and not a design fault, but until it is fixed the anchoring cannot be shown end to end. The chain is a local development node, so the anchored roots are not publicly verifiable.

P338: 7.10  Android SMS Gateway

P339: The Kotlin application keeps a WebSocket connection to the backend. When the gateway needs to send an OTP to a phone number, it sends a job over the socket and the app sends the SMS using a registered DLT template, as required for commercial SMS in India. Devices are registered by an administrator and authenticated with signed JWTs.

P340: 7.11  Web Dashboard

P341: The frontend is a React 19 single-page application with OTP login, a search page, and a results page that shows matched records, the risk score with its factors, and the AI analysis when present. Hashing runs entirely in the browser.

P343: TESTING

P344: 8.1  Approach

P345: We tested at three levels. Unit tests cover single functions, such as OTP handling, hashing and Merkle tree construction. Integration tests run several modules together, for example the full request path from OTP verification through search, scoring and audit logging. System checks run the real services and send real HTTP requests to them. Because earlier versions of the project reported features that did not work, we added a rule: a result counts only if we saw the raw output of running it, and an endpoint response is cross-checked against the source code.

P346: 8.2  Test Environment

P347: Tests ran on a development machine and, independently, in a clean Linux environment built from an exported copy of the repository. Backend tests use the Node.js test runner and frontend tests use Jest. The Python service was run under FastAPI and called with curl.

P348: 8.3  Verification Methods

P349: Automated suites. The backend suite and the frontend suite were run to completion. The backend suite was run both with and without the development OTP bypass.

P350: Live HTTP checks. Search, OTP and AI endpoints were called on the running services, and the matching and scoring logic was then read in the source to confirm the behaviour.

P351: Determinism check. The severity classifier was called repeatedly with the same input and also re-instantiated; identical output confirmed that trained weights are loaded.

P352: Independent reproduction. The XGBoost accuracy was recomputed from the raw test data in a separate environment and gave 89.17%, against the 89.2% reported.

P353: Failure injection. The AI service was stopped during a search to confirm the gateway degrades instead of failing.

P354: Deployment check. The contract was compiled and deployed on a clean local chain, which is how the missing-deployer-key fault was found.

P355: 8.4  Results Summary

P356: The backend suite passes 101 of 101 tests in 26 suites and the frontend suite passes 50 of 50 in 3 suites. All live checks in Chapter 9 passed except automatic contract deployment. A report of what was tested and how is more useful than a pass count, so Chapter 9 lists each case with its type, input, expected result and outcome.

P357: 8.5  What Testing Did Not Cover

P358: No load test or system-level latency benchmark was run, so this report makes no throughput or latency claim; the 31 ms figure for UrlBERT is a single-call inference time. The OTP rate limits were not tested under adversarial request volume. Only email identifiers were included in the end-to-end privacy check (see Section 7.2 for phone numbers).

P382: CONCLUSION AND FUTURE ENHANCEMENTS

P383: BreachShield shows that a breach-lookup service can avoid receiving the identifier it is asked about. The browser hashes the identifier, the server sees a 20-bit prefix, and access is limited to OTP-verified users. Around that core, the prototype combines several sources, an explainable risk score, a pretrained URL classifier and a Merkle-batched audit log anchored by a smart contract. The backend and frontend test suites pass (101/101 and 50/50). In the severity benchmark, XGBoost reached 89.2% accuracy on 157 test records, ahead of the CNN (66.2%), Transformer (48.4%) and RNN (44.6%). This agrees with published findings that trees remain strong on medium-sized tabular data [9].

P384: Limitations. These are open in the current code and are stated here so the results above are not over-read.

P385: Automatic deployment of the anchor contract fails when no deployer private key is set, so end-to-end anchoring is not demonstrated in a clean run. The chain is local, so roots are not publicly verifiable.

P386: Two of the four source adapters (phishing feeds, threat intelligence) make no network calls. Only the local catalog and the Telegram source return real data.

P387: Because search needs login, the server learns who is searching, although not which identifier in a bucket. Stronger protocols exist but cost more [3].

P388: The CRITICAL severity class has nine test records. The XGBoost model is not part of the production score.

P389: No system-level latency or load benchmark was run. OTP limits were not tested under adversarial load.

P390: CONFIRM before submission: (a) whether phone-number normalisation now matches between browser and server; (b) whether raw identifiers or phone numbers are still written to local JSON files (sessions, OTP records, audit logs, per-record files), which would contradict a privacy claim; (c) whether the Telegram source stores the raw target. Edit this list to match the current code.

P391: Future enhancements. In priority order: (1) supply the deployer key and re-verify a clean automatic deployment; (2) connect at least one placeholder adapter to a real feed; (3) apply oversampling or class weighting to the rare severity classes and re-benchmark; (4) run a reproducible latency benchmark before making any performance claim; (5) evaluate private-set-intersection protocols as a replacement for the prefix design [3]; and (6) consider anchoring on a public test network, following the batching approach in [7], once local verification is complete.
